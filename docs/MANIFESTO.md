# Fitness Court — Product Manifesto & Technical Strategy

> **Living document.** This is the source of truth for product direction. Changes go through PRs. Architect (currently solo dev) can amend with justification; changes are logged at the bottom.

---

## Vision

Fitness Court is a modern multi-tenant SaaS platform for gyms, fitness studios and sports facilities.

The goal is to replace outdated gym management systems with a flexible, scalable and automation-first platform focused on:

- membership management
- subscription flexibility
- access control
- customer experience
- operational automation
- analytics
- scalability

The platform must support both small gyms and enterprise fitness chains. Architecture must be cloud-native and production-ready from the beginning — but **not over-engineered** for the current stage. Premature complexity is the enemy.

> **Codename note:** "Fitness Court" is a working name through v1.0. Final brand TBD. All product-facing strings live in one branding module so renaming is a one-file change.

---

## Core Product Philosophy

Most gym systems are rigid, outdated, hard to customize, with poor UX and operational inefficiency.

Fitness Court solves:

- subscription inflexibility
- weak automation
- fragmented workflows
- poor customer experience
- lack of operational visibility

The platform should feel modern, lightweight, scalable, intuitive, API-first.

## Primary Business Model — SaaS Multi-Tenant Platform

Every gym receives:

- isolated workspace
- dedicated subdomain (`iron.fitnesscourt.com`, `fitzone.fitnesscourt.com`)
- independent staff users
- isolated members and data

Reference models: Slack, Trello, Notion, Shopify.

## v1.0 Scope — What We Actually Ship First

> **This section was clarified during architecture phase.** v1.0 is intentionally narrow.

### v1.0 = Admin Web + Telegram Bot for members

- **Admin Web (Next.js)** — used by gym owners, managers, receptionists, trainers. This is where all operational work happens: managing members, registering check-ins, creating plans, marking payments.
- **Telegram Bot** — the **only** member-facing client in v1.0. Members:
  - link their gym membership to their Telegram account via one-time code generated by admin
  - view active plan, days remaining, visits remaining, expiration date
  - receive their **rotating QR code** for check-in
  - get notifications (expiration warnings, freeze status, class reminders if booking is enabled)
- **No mobile app in v1.0.** Mobile app is v2.0.
- **No member web portal in v1.0.** Telegram bot covers it.

### Why this scope

- Solo dev, 6–8 weeks. A separate member web app + auth + UI is 3+ extra weeks of work that a Telegram bot replaces in 1 week.
- Telegram has push, identity, payments, and a polished UI for free.
- Owners care about admin tooling first, member experience second.

## MVP Modules

### 1. Authentication & Authorization

- email + password login (admin web only)
- JWT access tokens + refresh tokens
- RBAC permissions
- tenant-aware auth (a user belongs to exactly one tenant in v1.0)
- password recovery
- 2FA deferred to post-v1.0

**Telegram bot auth is separate:** members do not have email/password. They authenticate to the bot by linking their Telegram user ID to a member record via a one-time linking code generated by admin staff (or shown on member's printed welcome page).

#### Roles

- super admin (Keybit/operator level, cross-tenant)
- gym owner
- manager
- trainer
- receptionist
- member (Telegram-only in v1.0)

---

### 2. Multi-Tenant System

- tenant-aware architecture
- subdomain routing for admin web (`{slug}.fitnesscourt.com`)
- isolated data access enforced at the query layer (every tenant-scoped query is filtered by `tenant_id` via a base repository / SQLAlchemy event hook)
- tenant middleware resolves `tenant_id` from subdomain or JWT claim
- tenant configuration per gym

#### Isolation strategy

Shared PostgreSQL cluster, **logical isolation** via `tenant_id` column on every tenant-scoped table. Row-level security (RLS) is **deferred** — application-layer enforcement is enough for v1.0 and faster to build. Revisit RLS when we onboard an enterprise customer that demands it or when we hit any cross-tenant data bug in production.

---

### 3. Membership Engine — core business logic

#### Membership types

- unlimited monthly
- limited visits (e.g. 8 visits / month)
- yearly plans
- recurring memberships
- one-time packages
- trial memberships

#### Advanced features

- dynamic freeze / pause
- prorated extension
- automatic resume by date
- partial freeze
- custom expiration rules
- hybrid plans (days + visits)

#### Freeze system — core differentiator

Members can:
- pause active membership
- resume later
- auto-resume by date
- preserve remaining visits
- freeze multiple times within configured limits

Admin controls:
- max total freeze days per plan
- max freeze count per plan
- freeze fees (optional)
- freeze policies per membership type

Freeze actions happen via admin web; members can *request* a freeze via the Telegram bot, admin approves. Direct member-initiated freeze is deferred to v1.1.

---

### 4. Check-In System

#### v1.0 methods

- **Rotating QR code** displayed in the Telegram bot. QR encodes a short-lived token (default TTL: 30 seconds) signed by the server. Member opens bot → taps "Show QR" → presents to receptionist scanner / front-desk tablet. Token is single-use within its TTL window.
- **Manual check-in** by receptionist from admin web (search by name/phone).

#### Why rotating, not static, QR

A static QR per member = a screenshot = unlimited free entries forever. Rotating + single-use + short TTL eliminates this. **This was missing from the original manifesto and is now mandatory.**

#### Deferred

- RFID — phase 2
- facial recognition — future

#### Features

- visit tracking with audit log
- occupancy limits per branch
- anti-passback (configurable cooldown between consecutive check-ins)
- duplicate prevention
- branch validation (member's plan is valid at this branch)

---

### 5. Customer Management (CRM)

- member profiles
- visit history
- active plans + plan history
- invoices and payment history
- internal notes and tags
- status management (active, frozen, expired, churned)

#### CRM actions

- lead capture and follow-up
- trial-to-paid conversion tracking
- inactive user detection (members with no check-ins in N days)

---

### 6. Payments & Billing

> **Scope change from original manifesto.** Stripe integration is **deferred from v1.0** to v1.1.

#### v1.0 — manual billing

- Admin marks payments as received (cash, bank transfer, external POS).
- Invoices generated as PDF and shown in member profile + sent to Telegram.
- Renewal reminders sent automatically before plan expires.

#### v1.1 — Stripe

- Stripe Checkout for new subscriptions
- recurring subscriptions
- automatic invoice generation
- refunds
- failed payment retries

#### Why defer Stripe

For 50 target gyms, most early-stage gyms in the target market settle payments outside the platform anyway (cash, local bank transfer). Building Stripe properly (webhooks, idempotency, retries, prorations, tax) is 1.5–2 weeks of focused work that delays v1.0. Manual billing covers the same operational workflow for the MVP customer profile.

#### Future

- local payment gateways
- Apple Pay / Google Pay

## Technical Stack

### Frontend (admin web)

- React 18 + Next.js 14 (App Router)
- TypeScript (strict)
- TailwindCSS + shadcn/ui
- TanStack Query for server state
- Zustand for client state (used sparingly)
- React Hook Form + Zod

### Backend

- Python 3.12
- FastAPI
- SQLAlchemy 2.x (async)
- Alembic for migrations
- Pydantic v2 for schemas
- aiogram 3.x for the Telegram bot (runs as a module inside the FastAPI app via webhook)
- Celery + Redis for background jobs and scheduled tasks (Celery beat)

#### Architecture style

- **Modular monolith.** Clear module boundaries (`auth`, `tenants`, `memberships`, `checkins`, `crm`, `billing`, `bot`, `notifications`) but one deployable. Microservices deferred indefinitely — revisit only if a clear scaling reason emerges.

### Database

- PostgreSQL 16
- `tenant_id` column on every tenant-scoped table, enforced via base repository
- audit log table for sensitive actions (payments, freezes, manual check-ins)

### Cache & broker

- Redis 7 — caching, rate limiting, Celery broker

### File storage

- Local filesystem in v1.0 (mounted Docker volume on the VPS)
- S3-compatible (Cloudflare R2) when we outgrow the VPS disk or add a second instance

### Background processing

- Celery worker + Celery beat
- Used for: notifications, scheduled jobs (freeze auto-resume, expiration reminders), invoice PDF generation, daily analytics rollup

## Infrastructure

### v1.0 deployment

- **Single Hetzner Cloud VPS (CX22, ~€4.5/mo).** Ubuntu 24.04 LTS.
- Docker Compose for orchestration.
- **Caddy** as reverse proxy + automatic Let's Encrypt TLS (simpler than Nginx + certbot for solo dev).
- Daily PostgreSQL backups to Cloudflare R2 (free tier).
- DNS + wildcard subdomain (`*.fitnesscourt.com`) on Cloudflare.

### v1.1+ scaling path

- Move DB to managed Postgres (Hetzner Managed DB or Neon)
- Move Redis to managed service
- Add a second app server behind a load balancer
- Move files to R2

### What we explicitly do NOT use in v1.0

- Kubernetes (massive overkill for 50 gyms on one box)
- Multi-region anything
- Microservices
- Custom infra (Terraform, Pulumi) — Docker Compose + a deploy script is enough

Revisit when: we hit 500+ active gyms, or a single VPS can no longer serve peak load, or we need 99.9%+ SLA.

## Observability

### v1.0

- **Sentry** (free tier) for error tracking — backend + frontend
- **Structured JSON logs** to stdout, viewed via `docker compose logs` or shipped to a log aggregator when needed
- **Uptime monitoring** via UptimeRobot (free tier) hitting `/health`

### Deferred

- Prometheus + Grafana — overkill at this scale. Sentry + good logs catch 95% of issues for the first 50 customers.

## Security Requirements

Mandatory from day one:

- HTTPS everywhere (Caddy handles TLS automatically)
- Passwords hashed with Argon2id
- JWT with short access TTL + refresh rotation
- RBAC enforced at the route + service layer
- Rate limiting on auth endpoints, QR generation, and bot webhook
- Audit log for sensitive actions
- Tenant isolation enforced at the query layer with tests
- Parameterized queries everywhere (SQLAlchemy handles this)
- CSRF protection on cookie-based flows; the admin web uses bearer tokens so primary risk is XSS — strict CSP + httpOnly refresh cookie
- QR tokens signed with HMAC-SHA256, short TTL, single-use enforced via Redis

## API Design

- REST, OpenAPI documented (FastAPI generates this automatically at `/docs`)
- Versioned: `/api/v1/...`
- JSON only
- Cursor pagination on list endpoints that can grow large
- GraphQL deferred indefinitely — REST is sufficient

## Mobile Strategy

- **v1.0:** Responsive admin web only. Members use Telegram bot.
- **v1.1+:** Member web portal (subset of admin web, member-only views) — only if Telegram is insufficient for some customer segment.
- **v2.0+:** React Native mobile apps for members (and later staff).

---

## Product Design Principles

The admin UI must be:

- fast
- minimal
- operationally efficient — low click count to common actions
- keyboard-friendly for receptionists (Cmd+K command palette, hotkeys)

Avoid:

- overdesigned interfaces
- enterprise complexity
- decorative animations

The Telegram bot must be:

- one-tap to QR
- self-explanatory (no manual needed)
- localized (RU + EN at minimum in v1.0; bot UI text lives in `branding/`)

---

## Scaling Strategy

- **Phase 1 (now):** single VPS, all services in Docker Compose.
- **Phase 2:** split out managed DB + managed Redis, keep app on VPS.
- **Phase 3:** horizontal scale — multiple app instances behind LB, read replicas, separate workers.

Premature scaling is the bigger risk than insufficient scaling.

## Non-Goals (v1.0)

Explicitly **not** building:

- AI features
- social network
- workout tracking ecosystem
- smartwatch integrations
- nutrition systems
- ERP complexity
- marketplace
- multi-tenant *per user* (one user = one gym in v1.0; multi-gym accounts deferred)

Focus: gym operations, memberships, automation.
